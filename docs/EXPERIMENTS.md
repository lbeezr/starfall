## Workflow

1. **Proposed.** Record the question, hypothesis, smallest bounded candidate, baseline, and observable acceptance criteria. Cover rule/save invariants, interruption/input, accessibility, visual/animation behavior and relevant tests; mark inapplicable items explicitly. Choose a concrete decision point, such as completion of a named seed comparison and native play scenario.
2. **Isolated trial.** Keep alternate rules, fixtures and assets outside the shipping target, preferably in offline tooling or a temporary exported native lab. If a runtime comparison is necessary, make its route explicit and record why it is needed and when it will be removed. Give each rule, save contract and material one owner; do not duplicate production logic to bypass its boundaries. Record exact source, commands, configurations, seed/device/OS and results.
3. **Decide.** At the decision point, choose **adopted**, **removed**, or **extended trial**. An extension must state the unresolved question, bounded remaining work and next decision point. Bot scores, a successful build or a still screenshot do not establish enjoyment, gesture correctness or working animations. Record failures and limits without weakening assertions or adding blanket retries.
4. **Adopt.** Move the verified behavior into the authoritative production owner and default route, or its explicitly intended optional product mode. Remove the temporary route, flag, duplicated candidate and unused assets. Rename active code/files to production domain names; update project membership, tests and executable tools. Keep persistent keys, encoded fields, RNG and accessibility/launch contracts stable unless explicitly migrated and tested. Do not rename historical evidence to imply it tested later code.
5. **Integrate.** Commit the bounded change separately from unrelated work; validate the actual integration tree in a clean checkout/export. Run repository hygiene, core tests, affected hosted/UI checks and a simulator build. Include Release when routes, build settings, resources or Debug-only fixtures change. Distinguish native interaction, visual/animation, actual VoiceOver and device evidence. Existing unrelated failures need a source-bound comparison and concrete follow-up; they must not be reported as passes. Merge verified batches promptly. Update this register, README, roadmap and engineering risks in the same batch.
6. **Remove.** Delete rejected runtime routes, candidate-only assets and dead code. Retain compact historical evidence or a clearly labelled offline reproduction only when it still answers a concrete comparison question. Record the removal decision and any retained artifact's purpose. Do not retain permanent pilot flags by inertia.

An adoption record needs: status/date, hypothesis and scope, baseline/source, acceptance criteria, commands/results, decision and rationale, remaining risks with trigger/verification, and the integrating commit or branch. Use `docs/evidence/<work>-<date>/README.md` for the record; raw logs and media belong in ignored artifacts or temporary storage. No new framework or automated experiment system is required.

## Naming and compatibility

Production Swift types/files use domain names (`FallingSky…`), not `Experiment` or `Pilot`. Keep genuine comparisons labelled and isolated. Historical `experiment.*` accessibility IDs, existing saved-state keys and supported launch arguments are compatibility contracts, not experimental runtime routes; retain them when a naming-only promotion does not require a migration. Document that exception beside the owner. Historical evidence and frozen pre-promotion save fixtures keep their original names/source attribution.
