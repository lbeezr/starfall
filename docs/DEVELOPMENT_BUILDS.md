# Identify the build you are testing

**Status:** Accepted · **Owner:** current implementer · **Updated:** 2026-10-17

Use two labels: **`dev.<ID>`** for work in progress and **`rc.1.<ID>`** for a selected release candidate. A correction to a release candidate becomes `rc.2.<ID>`. Keep the ordinary product version, currently `0.1.0`, separate. No beta/nightly channels are needed for this prototype.

## One Starfall app and automatic device updates

**Accepted direction, 2026-10-17:** The user wants one app now, including the approved constellation swipe. Integrate that interaction into `com.starfall.prototype`, retain its ordinary defaults/save keys and update in place. The user chose the regular app's 0-starlight round over the lab's 26-starlight round; both preference files were backed up before replacement. The single-app migration installed **Starfall · `dev.bc187c831e`** from main `ba348d7` by the LaunchAgent. The native menu and local `installed.json` identify each subsequent update. [Delivery evidence](evidence/one-app-updates-2026-10-17/README.md) records validation and the CI limit. The replacement was installed and its round/preferences verified unchanged before `com.starfall.constellations.candidate` was removed. Do not create another phone identity for build numbers or experiments.

The [local updater](../scripts/device-update.py) checks GitHub `lbeezr/starfall` main every two minutes while this Mac is awake and the user is logged in. It targets only the configured physical iPhone and `com.starfall.prototype`. It fetches into its own bare repository, archives committed main into a separate build directory, checks the exact main push's CI status, runs local core tests, then builds/signs with the existing local Xcode account and installs over the same bundle. It does not launch, uninstall, reset or transfer saves. Missing device, a known CI failure, failed local tests, signing or installation failures retain the existing app and retry on a later check; source and error logs remain local.

The initial adoption exposed a roughly twenty-minute remote CI wait; after the locally verified merged build and retained saves were checked, its handoff used local validation too. Development delivery runs local core tests and verifies the signed build without waiting for broader CI; that suite continues in parallel. This avoids the measured long CI wait on every iteration. An explicit failing CI conclusion holds a new install; cancelled/timed-out remote runs are reported as unavailable and local development validation remains required. An already delivered development app is not automatically rolled back. Release candidates still require their full acceptance matrix.

`scripts/build_identity.py` owns the runtime fingerprint for both current delivery and historical lab stamping. Runtime source/assets/core/config/project and package manifest/resolution changes produce a new `dev.<ID>`; Markdown documentation (including nested READMEs) and test-only changes do not reinstall. The compiled Info.plist and native Sky menu show `StarfallBuildID`. The updater records the full source commit and installed fingerprint locally. A build failure never marks a revision installed, and an install retry can reuse the verified signed build. A process lock prevents overlapping runs.

Setup, status and disable commands are in [scripts](../scripts/README.md). The local LaunchAgent is copied into Application Support so archiving an implementation worktree cannot break delivery. Its script is installed explicitly; it does not self-modify on every fetch. Xcode signing/trust and device availability remain necessary; a locked phone can defer installation. Routine development uses the accessibility cadence below. Full VoiceOver sessions are not part of the updater. CI uses the explicit development matrix from `scripts/native_test_plan.py`; the RC matrix restores the named actual VoiceOver sessions. Selected tests retain their assertions and zero-skip counts.

The original [lab installation evidence](evidence/constellation-trace-2026-10-17/README.md) remains bound to `dev.fecfaa150d`; it does not establish this adoption/update pipeline's results.

## Accessibility checks by build stage

**Accepted 2026-10-17:** Reserve full actual VoiceOver sessions for release candidates, including the first release. Development builds can continue through gameplay polish and integration with lightweight checks. This cadence governs current work where older engineering notes name an earlier VoiceOver trigger; historical test results remain unchanged.

| Stage | Required scope |
| --- | --- |
| `dev.<ID>` | Preserve accessible controls, labels/values, non-color cues and equivalent committed outcomes. Run affected source, hosted/UI assertions and relevant layout/Dynamic Type checks alongside normal change validation. Enabling VoiceOver, listening to speech and running a full screen-reader playthrough are not routine development or experiment-adoption gates. |
| Targeted VoiceOver work | When fixing a reported VoiceOver defect or explicitly asked to check VoiceOver, reproduce and verify the affected behavior with actual VoiceOver. Keep the session scoped to the defect and related paths; this does not require the full release matrix. Ordinary visual or gesture iteration alone does not trigger it. |
| `rc.N.<ID>` | Run full actual VoiceOver acceptance on the selected candidate before release. Cover the current shipping flows and supported modes, retain source/build/device/OS evidence and resolve release-blocking failures. Automated labels/audits cannot substitute for focus, speech and activation checks. |

For the first release candidate, play a complete round with actual VoiceOver on a physical iPhone: explore star position/type/value, navigate matching groups, select and clear, pause/manual advance, handle arrivals and announcements, reach outcomes/replay, restore a saved round, and enter/leave Settings with usable focus. If constellation drawing is adopted, also verify its accessible select/count/value, release and cancel actions. Include interruption/focus continuity and the applicable Reduce Motion/large-text combinations. Record additional supported-device/layout coverage and any omissions in the candidate acceptance record; do not infer them from one phone.

Carry forward source-bound evidence for unchanged behavior. For later candidate fixes, rerun affected flows and related regression cases; repeat the full session only when changes invalidate its coverage. Identify the evidence used for the final candidate and why earlier results still apply. No release is accepted with required VoiceOver flows untested or known blocking defects unresolved.

During development, record **“Actual VoiceOver: deferred to RC; not run on this development build”** in the relevant acceptance record. Keep known defects and their release follow-up visible; deferral is neither a pass nor a reason to halt unrelated iteration. Routine progress updates need not repeat that planned deferral. Keep normal touch, full-motion, Reduce Motion, automated accessibility and actual VoiceOver evidence distinct; do not disable or weaken existing assertions to satisfy this cadence.

The exact-source main CI status is checked again immediately before installation after local validation/signature verification. A newly known failure holds installation and retains the verified build for retry. The versioned runtime-input recipe covers root Package.swift/Package.resolved and project-workspace resolution files; its adoption causes one deliberate fingerprint change.

## Reject stale delivery and detect external replacements

After the October 18 stale-checkout incident, delivery verifies the OS-owned installation URL and bundle version on the configured phone before reporting “up to date.” `installed.json` includes those fields alongside source/build identity. An external install changes the app's container URL; a missing app, legacy receipt or version mismatch also requires a verified current-main install. Unknown/malformed inventory defers delivery. This installation identity links the actual app to a verified install receipt; it is not a remote binary hash or an OS permission restriction.

Fetched main must descend from the last delivered/checked main. A rollback, divergent history or missing ancestor object holds delivery. Main is fetched again after local tests/signature checks; if it changed during validation, delivery defers rather than installing the older snapshot. The archive's runtime fingerprint is rechecked too. After installation, device inventory must match the installer result and compiled bundle version before a receipt is written. Failed validation leaves the receipt intact and reports the error; it never claims an unverified installation is current.

Use the canonical updater for production. Direct Xcode/`devicectl` installs from feature checkouts are prohibited by the repository's delivery contract. This Mac still has technical signing/install access: a process with that access can bypass the tooling. The service detects such replacements on its next check and repairs them only when source, local tests, signing and existing CI policy permit. True prevention of every privileged bypass would require an OS/account permission boundary outside this fix.
